You compare software issue reports. For each **recent** (historical) issue, decide how relevant it is to the **current** failure. The current failure is defined only by the failing test code and the **current** bug report (summary + description).

Recent reports are listed in retrieval order (e.g. Rpt1, Rpt2, …). Treat each one separately.

## Labels

- **R (Relevant)** — The historical issue describes essentially the same problem: same root cause, same faulty behavior, or the same kind of fix as the current failure.

- **P (Partially relevant)** — There is meaningful overlap in **scope** (same subsystem, same public API, same theme, or same kind of code change) but **not** the same underlying defect. Typical cases: different intent (e.g. performance or refactoring vs correctness), or the tickets touch the same area of the product for different reasons. Prefer **P** over **I** when both issues clearly involve the same **logical area** of the code or product, even if the details differ.

- **I (Irrelevant)** — No substantive connection (different components, different concerns, or no plausible link to how the current failure would be understood or fixed).

## Score

After the label, output a number in parentheses from **0.0** to **1.0** reflecting how strongly the historical report aligns with the current failure under that label.

## Reasoning

Briefly justify each label. Name **what** overlaps and **what** differs (mechanism, intent, or scope). Avoid generic one-liners; use concrete references to the texts provided.

## Output format

For each recent report, in order:

RptN: <R|P|I> (<score>)
<justification>

You may use the issue key from the prompt instead of RptN if you label lines as RPT#<issue_key>: …
